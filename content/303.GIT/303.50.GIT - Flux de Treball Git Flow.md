# Flux de Treball: Model GitFlow
Introduït per **Vincent Driessen** el 2010, el model GitFlow està dissenyat per a projectes amb un cicle de llançament programat i que requereixen un control rigorós sobre les versions de producció. [^1]

> [!NOTE] **Objectiu principal**
> Separar clarament l'estat de **producció**, el **desenvolupament actiu** i el **treball en curs**, minimitzant riscos i [[./303.25.GIT - Resolució de Conflictes en package-lock|conflictes]] en equips mitjans o grans.

---
## 1. [[./303.01.GIT - Introducció i Arquitectura|Arquitectura]] de [[./303.20.GIT - Conceptes Bàsics de Branca|Branques]]
A diferència de models més simples, GitFlow utilitza la branca `develop` com a eix central, deixant la branca `main` exclusivament per a codi estable.
### Branques Permanents (Infinites)
* **`main` (Master):** Representa el codi en producció. Cada [[./303.10.GIT - El Commit i Conventional Commits|commit]] és una versió estable i desplegable, normalment identificada amb una etiqueta de versió (**tag**).
    * *Protecció:* No es permeten *pushes* directes. Requereix [[./303.40.GIT - Treball en Remot i Push|Pull]] Request ([[./303.41.GIT - Traçabilitat de Commits i Pull Requests|PR]]) i CI/CD aprovat.
* **`develop`:** Branca d'integració per a noves funcionalitats. És l'estat de "pre-producció" on resideix el codi que anirà a la propera versió.
    * *Protecció:* Requereix PR i revisions de codi.
### Branques Temporals (De suport)
| Tipus de Branca | Origen | Destí | Vida Útil | Propòsit |
| :--- | :--- | :--- | :--- | :--- |
| **`feature/*`** | `develop` | `develop` | Mitjana | Noves funcionalitats. |
| **`bugfix/*`** | `develop` | `develop` | Curta | Correccions en fase de desenvolupament. |
| **`release/*`** | `develop` | `main` i `develop` | Curta | Preparació, QA i metadades de versió. |
| **`hotfix/*`** | `main` | `main` i `develop` | Molt curta | Correcció d'errors crítics en producció. |

## 2. Operativa i [[./303.53.GIT - Comparativa de Fluxos de Treball|Fluxos de Treball]]

### A. Nova funcionalitat (`feature`)
Es desenvolupa de manera aïllada per no embrutar la branca d'integració fins que estigui llesta.
1. Crear `feature/nom-funcionalitat` des de `develop`.
2. Desenvolupament i commits locals.
3. Obrir Pull Request cap a `develop`.
4. Revisió, correcció de conflictes i **[[./303.24.GIT - Merge i Mergetool|Merge]] a `develop`**.

### B. Preparació d'un llançament (`release`)
Quan `develop` té prou funcionalitats per a una nova versió:
1. Crear `release/vX.Y.Z` des de `develop`.
2. Realitzar ajustos finals (versions, documentació) i correccions de darrera hora.
3. **Merge a `main`** + Crear **Tag** (`vX.Y.Z`).
4. **Merge de tornada a `develop`** per assegurar que els ajustos finals es mantinguin.

### C. Hotfix en producció
Per a errors crítics que no poden esperar al següent cicle de llançament:
1. Crear `hotfix/descripcio` des de `main`.
2. Aplicar la correcció urgent.
3. **Merge a `main`** + Crear **Tag**.
4. **Merge de tornada a `develop`** per mantenir la paritat.

## 3. Gestió de Versions (Etiquetatge)

Les etiquetes representen fites oficials. L'estàndard és utilitzar **[[./303.12.GIT - Versionament Semàntic|Semantic Versioning]]** (vMajor.Minor.Patch).

### Exemple de finalització d'un Hotfix:
```bash
# Integrar a producció
[[303.22.GIT - Checkout|git checkout]] main
git merge hotfix/fix-critical-bug
git tag -a v1.2.1 -m "Hotfix v1.2.1: Correcció de seguretat"
git push origin main --tags

# Sincronitzar amb desenvolupament
git checkout develop
git merge hotfix/fix-critical-bug
git push origin develop
```

## 4. Beneficis i limitacions

### Beneficis
* **Control i Estabilitat:** Producció sempre està protegida de canvis experimentals.
* **Traçabilitat:** L'estructura de branques facilita saber exactament què hi ha a cada entorn.
* **Paral·lelisme:** Permet que diversos equips treballin en funcionalitats diferents i en la preparació del llançament simultàniament.

### Limitacions i Context Modern
Malgrat la seva robustesa, GitFlow ha rebut crítiques en entorns de **Continuous Delivery (CD)**:
* **Merge Hell:** Les branques `feature` de llarga durada poden divergir excessivament, provocant conflictes complexos en integrar-les.
* **Burocràcia:** El procés de múltiples fusions pot reduir la velocitat de lliurament.
* **Contradicció amb CI:** Autors com Dave Farley argumenten que la Integració Contínua real implica integrar al tronc principal cada dia, cosa que GitFlow retarda deliberadament. [^2]

> [!TIP] ideal  
> GitFlow és ideal per a programari que es distribueix en versions tancades (ex: aplicacions mòbils, programari de sistemes). Per a serveis web amb desplegament diari, considereu models més àgils com **[[./303.51.GIT - Flux de Treball Trunk Based Development|Trunk-Based Development]]**.
