# Flux de Treball: Trunk-Based Development (TBD)

El **Trunk-Based Development** és el model predilecte per a equips d'alt rendiment i entorns DevOps moderns. A diferència de [[303.11.b.GIT_flux de treball_model_git_flow|GitFlow]], aquest model prioritza la velocitat d'integració i la simplicitat de l'historial.

> [!IMPORTANT] **La idea central**
> Tot el desenvolupament gira al voltant d'una **única [[./303.20.GIT - Conceptes Bàsics de Branca|branca]] principal** (*trunk*, normalment `main`). L'objectiu és integrar canvis petits de manera constant per evitar "l'infern de les fusions".

---

## 1. Filosofia: Flux sense Interrupcions
En aquest model, les branques de llarga durada desapareixen. La premissa és senzilla: **com més petit és el canvi, menor és el risc.**

* **Sense branca `develop`:** Tot es fusiona directament a `main`.
* **Branques de vida curta (Short-lived):** Si s'utilitzen branques, aquestes duren unes hores o, com a màxim, un parell de dies.
* **Integració contínua:** El codi s'integra diverses vegades al dia.

---

## 2. Els Pilars Tècnics
TBD no és només una política de Git, és una disciplina que requereix una infraestructura sòlida per no trencar la branca principal:

* **CI (Integració Contínua) Robusta:** Cada [[./303.10.GIT - El Commit i Conventional Commits|commit]] ha de disparar tests automatitzats immediatament. El trunk ha d'estar "sempre verd" (desplegable).
* **Proves Automatitzades d'Alta Cobertura:** La confiança en el codi no ve d'una fase de QA manual, sinó d'una suite de tests exhaustiva.
* **[[./303.52.GIT - Tècniques Avançades per a TBD a Escala|Feature Flags]] (Commutadors de Funcionalitat):** Permeten integrar codi de funcionalitats incompletes al trunk sense activar-les en producció.
* **[[./303.24.GIT - Merge i Mergetool|Merge]] Queues (Cues de Fusió):** En equips grans, gestionen les fusions simultànies per assegurar la integritat del codi final.

---

## 3. L'Operativa Diària

### El Flux de Treball Típic
1.  **Sincronització:** Estar al dia amb els darrers canvis de `main`.
2.  **Branca curta:** Crear una branca tipus `feat/nom-breu` des de `main`.
3.  **Desenvolupament atòmic:** Commits petits i coherents.
4.  **[[./303.41.GIT - Traçabilitat de Commits i Pull Requests|PR]] i Revisió ràpida:** El codi es revisa i es fusiona immediatament després de passar el CI.
5.  **Eliminació:** Es borra la branca local i remota un cop feta la fusió.

### Correccions urgents (Hotfixes)
No existeix un flux especial. Si hi ha un error a producció, es tracta com qualsevol altra tasca: branca curta, fix, PR i merge a `main`. La velocitat del pipeline de CI/CD permet que el fix arribi ràpidament a l'usuari.

### Gestió de Releases
* **Deploy Continu:** Cada merge a `main` es desplega automàticament. Les versions són identificades pel hash del commit.
* **Versions Etiquetades:** Es manté el desenvolupament a `main` i es creen **tags** en commits específics per marcar versions oficials (`v1.2.0`).

---

## 4. Feature Flags: El secret del TBD
Per evitar branques que durin setmanes mentre es desenvolupa una funcionalitat complexa, s'utilitzen les **Feature Flags**.

> El codi "incomplet" es fusiona a `main` però es manté inactiu mitjançant un condicional en el codi o una eina de [[./303.04.GIT - Configuració i Inici|configuració]]. Això permet provar la integració constant sense afectar l'experiència de l'usuari.

---

## 5. Comparativa: Quan utilitzar-lo?

| Escenari            | Trunk-Based Development              | GitFlow                              |
| :------------------ | :----------------------------------- | :----------------------------------- |
| **Equips**          | Alta maduresa i disciplina.          | Equips que necessiten control rígid. |
| **Velocitat**       | Molt alta (desplegament continu).    | Lenta (cicles programats).           |
| **Complexitat Git** | Baixa (poca gestió de branques).     | Alta (moltes fusions i branques).    |
| **Dependència**     | Depèn totalment de l'automatització. | Depèn de processos de QA manuals.    |

### Recomanat si:
* Vols fer **Continuous Delivery/Deployment**.
* Tens un pipeline de tests ràpid i fiable.
* L'equip té cultura de commits petits i revisió ràpida.

### Evita'l si:
* No tens tests automatitzats.
* L'equip tendeix a fer "commits gegants" de milers de línies.
* Has de mantenir múltiples versions de producció simultàniament (ex: versió 1.0 i 2.0 a la vegada).

---

> **Reflexió:** El Trunk-Based Development **no és més simple, és més estricte**. Exigeix una excel·lència tècnica que, un cop assolida, permet molta agilitat.
