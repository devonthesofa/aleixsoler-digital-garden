# GitFlow vs. Trunk-Based: Guia de Decisió

L'elecció entre un model o un altre no és una qüestió de preferència personal, sinó d'estratègia operativa. A continuació, analitzem com l'estructura de les [[./303.20.GIT - Conceptes Bàsics de Branca|branques]] condiciona el rendiment de l'equip.

---

## 1. Comparativa Estructural i Topològica

La "forma" del teu historial de Git diu molt sobre com treballa el teu equip.

### Model [[303.11.b.GIT_flux de treball_model_git_flow|GitFlow]]: El Graf Multilineal
Es caracteritza per l'aïllament. És una xarxa complexa on les funcionalitats viuen en "bombolles" durant dies o setmanes abans de col·lisionar amb la realitat.
* **Visualment:** Moltes línies paral·leles i fusions periòdiques.
* **Risc:** Les fusions són esdeveniments d'alt risc ("[[./303.24.GIT - Merge i Mergetool|Merge]] Hell").
### Model [[303.11.c.GIT_flux de treball_trunk_based development|Trunk-Based]]: El Graf Lineal
Es caracteritza per la integració. Les branques són meres "pestanyes" temporals que tornen al tronc gairebé immediatament.
* **Visualment:** Una única línia central amb petites ramificacions que neixen i moren ràpidament.
* **Risc:** Un error a la branca principal afecta a tothom, però es detecta a l'instant.

---

## 2. L'Impacte en les Mètriques DORA

Les mètriques **DORA** (DevOps Research and Assessment) són l'estàndard per mesurar l'eficiència en el lliurament de programari. El Trunk-Based Development és, per definició, el model que millor s'alinea amb l'alt rendiment.

| Mètrica DORA | Rendiment en **GitFlow** | Rendiment en **Trunk-Based** |
| :--- | :--- | :--- |
| **Lead Time for Changes** | **Alt:** El codi triga dies o setmanes a arribar a producció. | **Baix:** El canvi pot estar desplegat en hores o minuts. |
| **Deployment Frequency** | **Baixa:** Es desplega per lots (releases), setmanal o mensualment. | **Alta:** Desplegament constant (diversos cops al dia). |
| **Change Failure Rate** | **Variable:** Les fusions grans solen amagar errors complexos. | **Baix:** Canvis atòmics que són fàcils de provar i validar. |
| **Time to [[303.63.GIT - Restore|Restore]] (MTTR)** | **Alt:** Costa identificar quin canvi del "lot" ha provocat l'error. | **Baix:** L'últim [[303.10.GIT - El Commit i Conventional Commits|commit]] és gairebé sempre el culpable. |

---

## 3. Cost de Coordinació vs. Velocitat

### GitFlow: Optimitzat per a l'Estabilitat Planificada
És ideal quan el llançament és un esdeveniment que requereix coordinació humana (màrqueting, formació a clients, aprovacions legals).
* **Avantatge:** Control total sobre què entra i quan surt.
* **Cost:** "Fricció operativa". El temps invertit a gestionar branques és temps que no s'inverteix a escriure codi(si es que algú l'escriu hores d'ara xd).

### Trunk-Based: Optimitzat per al Flux Continu
És el model de referència per a SaaS i productes digitals que necessiten validar hipòtesis ràpidament.
* **Avantatge:** Elimina els colls d'ampolla de les fusions. Tot flueix sense interrupció.
* **Cost:** Requereix una inversió massiva en **automatització** (CI/CD) i una cultura de revisió de codi extremadament àgil.

---

## 4. Matriu de Decisió per a Líders

| Si el teu escenari és... | El model recomanat és... |
| :--- | :--- |
| Desenvolupes una App mòbil o programari amb versions tancades. | **GitFlow** |
| Tens un equip jove o sense tests automatitzats. | **GitFlow** (com a pas previ) |
| Fas Continuous Deployment (SaaS, Web). | **Trunk-Based** |
| Tens un equip sènior amb alta disciplina de testing. | **Trunk-Based** |
| El lliurament depèn d'aprovacions manuals externes. | **GitFlow** |

---

> [!NOTE] **El Consell de l'Arquitecte**
> Molts equips comencen amb **GitFlow** per por al caos, però a mesura que automatitzen els seus tests, el model natural de creixement és simplificar cap a **Trunk-Based**. La simplicitat en Git sol ser sinònim de maduresa tècnica.
