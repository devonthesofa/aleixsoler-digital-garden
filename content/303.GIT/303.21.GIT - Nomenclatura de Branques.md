# Branch naming - convenció de noms de branques [^1][^2]

> [!NOTE] Important
> Una bona convenció de noms de branques facilita la **traçabilitat**, la **revisió de codi** i la **comprensió del flux de treball**.
> L’objectiu és que el nom de la branca expliqui **què s’està fent i per què** sense obrir el codi.
## Estructura general

```text
<category>/<reference>/<description>
```

## 1. Category

La branca ha de començar sempre amb una categoria clara. Categories recomanades:
- `feature` - Afegir, modificar o eliminar una funcionalitat.
- `bugfix` - Corregir un error.
- `hotfix` - Solució urgent, normalment fora del flux habitual.
- `test` - Proves o experiments sense impacte directe en producció.
- `refactor` - Si és purament un refactor, llegeix la part  [[303.21.GIT - Nomenclatura de Branques#Per què no posar refactor com a categoria de branca|Per què no posar refactor com a categoria de branca]]
- `release` - Per preparar noves versions

Si no és urgent ni experimental, probablement és `feature` o `bugfix`.

## 2. Reference
Després de la categoria, afegeix la referència del *ticket* o *issue* associat.
- Si hi ha referència → usa-la (`JIRA-123`, `#42`, etc.).
- Si no n’hi ha → usa `no-ref`.

Exemples:

```text
feature/JIRA-123/...
bugfix/no-ref/...
```

## 3. Description

Descripció curta del propòsit de la branca.
- En *kebab-case*
- Clara i concisa
- Sense caràcters especials

Pots reutilitzar el títol del ticket substituint espais i símbols per `-`.

Exemples:
```text
feature/JIRA-123/add-login-form
bugfix/42/fix-null-pointer-error
test/no-ref/api-rate-limit-experiment
hotfix/no-ref/rollback-broken-deploy
```

## Resum
* Categoria clara → intenció clara
* Nom curt → branca llegible
* Una branca = un propòsit

## Per què no posar refactor com a categoria de branca

Una branca serveix per descriure l’objectiu del treball, no la naturalesa tècnica exacta del canvi.

Un refactor gairebé sempre existeix per alguna raó:
- preparar una feature
- arreglar un bug
- reduir deute tècnic associat a una tasca

Si poses:`refactor/JIRA-123/cleanup-auth-service` Estàs explicant com treballes, no per què.
En canvi: `feature/JIRA-123/improve-auth-flow` explica la intenció real, encara que internament facis refactors.

Però queda clar, que si aquesta branch la fàs servir per fer purament un refactor, doncs si que té sentit usar la categoria de `refactor`, per exemple, algo acceptable seria: `refactor/no-ref/simplify-permission-model`
