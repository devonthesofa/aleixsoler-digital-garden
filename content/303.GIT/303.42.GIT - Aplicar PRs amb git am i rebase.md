# Aplicar Pull Requests ([[./303.41.GIT - Traçabilitat de Commits i Pull Requests|PR]]) amb `git am` i `[[303.26.GIT - Rebase|rebase]]`

## [[./303.01.GIT - Introducció i Arquitectura|Introducció]]: Què és un "Patch"?
Abans de l'existència de plataformes visuals com [[./303.80.GitHub - Plataforma i Flux|GitHub]] o GitLab, els desenvolupadors de programari lliure (com els del nucli de Linux) col·laboraven enviant canvis per **correu electrònic**. Un **patch** (o pedaç) és un fitxer de text que conté no només les línies de codi que han canviat (el *[[./303.31.GIT - Comparació amb Diff|diff]]*), sinó també la metadada del [[./303.10.GIT - El Commit i Conventional Commits|commit]]: autor, data i missatge.
### Per què es segueixen fent servir?
- **Sistemes aïllats:** Quan vols moure codi entre servidors que no tenen connexió de xarxa entre ells.
- **[[./303.53.GIT - Comparativa de Fluxos de Treball|Fluxos de treball]] "Mailing List":** Encara és l'estàndard en projectes gegants com Linux o PostgreSQL.
- **Netedat:** Permet aplicar canvis d'una [[./303.20.GIT - Conceptes Bàsics de Branca|branca]] a una altra sense "embrutar" l'historial amb merges, mantenint una línia de commits totalment plana.

## Mètode 1: Fent servir `git am` (Patches)
`git am` significa "Apply Mail" (aplica correu). Està dissenyat específicament per llegir el format generat per `git format-patch`.

### 1. Exportar els patches
Des de la branca on tens la Pull Request, exporta tots els commits a fitxers `.patch`:
```bash
git format-patch primer_commit_PR~1..HEAD -o patches/nom-carpeta/
```
*Això crearà un fitxer numerat per cada commit dins la carpeta indicada.*
### 2. Preparar la branca de destí
Canvia al directori del projecte de destí i crea (o mou-te a) la branca on vols aplicar els canvis:
```bash
[[303.22.GIT - Checkout|git checkout]] -b rolling
```
### 3. Aplicar els patches
```bash
git am patches/nom-carpeta/*.patch
```

### Gestió de [[./303.25.GIT - Resolució de Conflictes en package-lock|conflictes]] en `git am`
Si el procés falla perquè el codi base ha canviat massa:

1.  **Aplicar manualment el patch conflictiu:**
    ```bash
    git apply patches/nom-carpeta/XXXX-fitxer-que-falla.patch --reject
    ```
2.  **Resoldre diferències:** Git crearà fitxers `.rej` amb els fragments que no ha pogut col·locar automàticament. Aplica'ls a mà i **esborra els fitxers `.rej`**.
3.  **Afegir canvis:** `git add --patch [fitxers_modificats]`
4.  **Continuar el procés:** `git am --resolved`
    *(Per cancel·lar: `git am --abort`)*

## Mètode 2: Fent servir `rebase --onto`
Aquest mètode és una alternativa moderna que no genera fitxers externs, sinó que "reescriu" els commits directament d'una branca a una altra dins del mateix repositori.

> [!WARNING] **Atenció al [[./303.06.GIT - Estats dels Fitxers|Working Directory]]**
> No pots fer un rebase amb canvis pendents. Si en tens, fes un `[[303.64.GIT - Stash|git stash]]` abans de començar i un `git stash pop` en acabar.

### Passos a seguir:
1.  **Crear branca de treball:** `git checkout -b rolling`
2.  **Crear branca temporal:** Crea una referència al punt "base": `git checkout -b tmp_prXXXX`
3.  **Apuntar la branca destí al final de la PR:**
    ```bash
    git branch rolling -f sha_ultim_commit
    ```
4.  **Executar el Rebase Estratègic:**
    ```bash
    git rebase --onto tmp_prXXXX sha_primer_commit~1 rolling
    ```
    *Això "talla" els commits de la PR i els "enganxa" sobre la branca temporal.*
5.  **Neteja:** `git branch -d tmp_prXXXX`
